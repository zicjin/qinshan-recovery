# Database behavior progress; Oracle single mainline after PostgreSQL stop-loss

2026-10-20. Ticket 15 remains **incomplete**. The original fixture-only report was withdrawn; current evidence uses real SQL and a real owned-application attempt in disposable databases.

`t15-postgresql-probe.json` records PostgreSQL 16.15 amd64 SQL results from the digest-pinned ECR image. The 18 checks concern synthetic rows and schema behavior: active/wrong-digest/inactive predicates, permission ancestry, pagination/filter/stock/aggregate queries, sequence consumption across rollback, timestamp formatting, regex, small text/binary LOB round trips, commit/rollback, and SQLSTATE 23505. The runner records image/container identity, source/SQL hashes, isolated `network=none`, no published ports or host mounts, and container/anonymous-volume cleanup. A separate real negative control verifies an invalid SQL object produces failure rather than passing evidence.

Oracle 26ai Free Release 23.26.3 executed the same 18 synthetic-schema probes in `t15-oracle-probe.json`. It requires a fresh Docker internal bridge because its IPC initialization fails without a non-loopback private IP. Evidence checks internal=true, one endpoint belonging to the probe container, no published ports/host mounts, and network cleanup. The Oracle image provenance record binds the original manifest/config/six layer hashes to the Docker-normalized imported image without equating the original and imported digests. Actual invalid-object controls pass for both engines; the Oracle control also verifies internal network deletion.

The separate PostgreSQL application stop-loss (`t15-postgresql-application-stoploss-20261020.json`) started the owned application against PostgreSQL 16.15, reached the database through the real login and report DAO paths, and recorded the existing Oracle-specific failures: login `NVL` and report `TO_CHAR` both returned SQLSTATE `42883`; HTTP login became `500 LOGIN_UNAVAILABLE`; anonymous personnel, equipment, consumables, report, and the newly registered menu route remained `403` with the existing permission-denied boundary. The menu route is therefore an anonymous denial observation, not a permission-tree compatibility result. Invalid-object, provenance, internal-network/no-port/no-bind isolation, and cleanup controls passed. `executed-pass` means the expected failure observations were captured, not that PostgreSQL is compatible.

The application attempt does not justify a SQL shim, Oracle semantic rewrite, or long-term dual stack. Oracle is the single mainline/fallback decision for this recovery effort; PostgreSQL exploration stops unless a separately approved compatibility plan changes that decision. The six application slices, full Oracle comparison and complete permission-tree behavior remain open.
